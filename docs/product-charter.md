# ChangePassport 项目章程

## 一句话定位

从 GitHub 的真实发布记录生成可验证、可导出的变更证据包，并明确标记缺失流程；**不自动生成“合规结论”**。

## 目标用户

需要向审计方、客户或内部治理团队说明“这次发布是怎么来的”的小型工程团队：他们有 GitHub PR / Review / CI 记录，但部署、回滚、例外和工单链接散落在聊天记录、表格和人的记忆里。首个画像：**单个到少数几个仓库、有发布留痕压力、但没有专职治理团队的团队**。

## 要解决的问题

团队每次补发布材料都要人工翻 GitHub、聊天记录和表格；结果不可复现，缺了什么靠猜，流程例外往往在事后才被发现。_change passport_ 把可自动获取的 GitHub 事实与人工声明分开记录，并明确标出缺口与数据出处。

## 首个版本范围

- 本地 Python CLI：`init` / `build` / `verify` / `render`。
- GitHub Action：以 **report-only** 运行，产物作为 Workflow Artifact 保存。
- 开放 `schemas/v1/passport.schema.json`。
- JSON 与 Markdown 两种输出；Markdown 只渲染已有事实，不重新获取或推断。
- 只收集 PR 基本信息、Commits、Reviews、Checks/Status，以及用户显式配置的工单、部署、回滚与例外信息。
- 每次生成记录生成器版本、生成时间和内容摘要。

## 非目标（首版明确不做）

- 后端、数据库、多租户控制面、账号体系、SSO、复杂 RBAC、计费系统。
- 默认遥测、客户代码持久化、把客户数据用于训练；核心链路不调用大模型。
- 自动读取全部源代码、连接生产环境、自动批准或拒绝发布。
- 通用工单平台、AI 风险评分、通用合规平台、大量第三方集成。
- 任何“保证通过 SOC 2 / ISO 27001 / 审计”的承诺。

## 证据边界（每个用户可见的声明）

1. GitHub 可查事实带来源 URL；人工填写的工单/部署/回滚/例外标为 `declared`，表示使用者声明，未做独立验证。
2. 查不到的数据写 `missing` 或 `unknown`，不推测审批、部署、测试或回滚事实。
3. 内容摘要（SHA-256）只用于检测内容变化；**不是**防篡改机制，也不是可信时间戳。
4. “审批通过”不等于“变更安全”；本报告不是审计意见或认证结论。
5. 日志默认脱敏：不打印 token、完整源代码或客户正文。

## 止损条件

- 第 14 天问题门不达标 → 换细分场景或问题，不扩建平台。
- 第 45 天没有 3 个已收款试点 → 停止托管控制面计划；无人付款则按免费工具维护。
- 第 90 天没有 2 个持续付费客户 → 停止扩建，保留可维护开源工具或转向有边界的咨询。
- 任一安全边界被破坏 → 先修复再继续，不以新增功能掩盖。

## 成功定义

工程可行（15 分钟内在测试仓库生成第一份有用证据包）、需求真实（团队能展示近期人工整理流程）、有人付款（真实收款的重复需求）——三者缺一不可。
