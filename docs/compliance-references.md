# 合规框架参考（仅帮助理解字段，不构成合规结论）

这份文档回答一个很窄的问题：**为什么证据包要收集“目的、审批、测试、部署、回滚、例外”这几类字段？** 它不提供认证意见，也不把公开解读当作标准原文。

## 公开资料中的常见关注点

公开解读普遍把 SOC 2 CC8.1（变更管理）和 ISO/IEC 27001:2022 附录 A 8.32 的关注点概括为：变更需要被授权、审批、测试、记录，并且要有可追溯的部署与回滚/例外处理记录[2](https://www.compliancebase.org/controls/soc-2/cc8-1)[4](https://governancedocs.com/iso-27001-change-management/)。一些面向团队的指南也把变更请求、风险/影响评估、审批、测试证据、回滚计划和事后复核列为审计抽样时常见的材料类型[1](https://quicktrustapp.com/blog/change-management-process-compliance)。

这些是**第三方解读**，不是 AICPA 或 ISO 标准原文，也不一定适用于每个组织的适用范围（SoA）或具体审计程序。它们只用来解释我们的字段为什么存在，不能用来推导“满足控制要求”。

## 与本工具字段的对应关系

| 常见关注点 | 本工具记录的字段 | 工具实际做的事 |
|---|---|---|
| 变更请求/目的 | `change.purpose`、`change.external_ticket` | 保存人工填写的编号与链接；查不到写 `missing` |
| 审批 | `reviews`、`approvals` | 只从 GitHub Review 中提取 APPROVED 事实与原始 URL；不推测 |
| 测试/CI | `checks` | 保存 Check/Status 名称、结论、时间和链接；失败会被策略报为缺口 |
| 部署 | `deployments` | 保存人工声明的环境、时间、操作者；标为 `declared`，未独立验证 |
| 回滚/例外 | `rollbacks`、`rollback_plan`、`exceptions`、`exception_review` | 保存人工声明与复核状态；缺失明确列出 |
| 可追溯性 | `provenance`、`content_digest` | 逐字段记录来源；摘要仅检测内容变化 |

## 必须同时说明的限制

1. **不是认证。** 本工具不保证通过 SOC 2、ISO 27001 或任何审计；是否充分、是否有效由组织与审计方判断。
2. **不等于控制有效。** 有审批不等于变更安全；有 Check 成功也不等于测试充分。
3. **不替代人工判断。** 风险/影响评估、职责分离、紧急变更事后复核等需要组织自己的流程与证据。
4. **不提供可信时间戳或防篡改证明。** SHA-256 摘要只能发现内容变了。
5. **不收集客户源代码或把数据用于训练。** 产物只含标识、时间、结论与链接。

## 使用方式

在访谈或试点中，可以用这份文档解释字段设计动机，但不要说“这个工具覆盖 CC8.1 / A.8.32”。准确的说法是：

> 它把团队已经存在的 GitHub 事实和人工声明整理成可导出的证据包，并明确标出缺口；是否能作为某项审计证据，由你们的审计方决定。
